# What MakeItLean guarantees, and what it does not

**In one paragraph.** When `mil audit` prints **AUDIT PASSED** for a frozen app, the implementation
has been proven, by Lean's kernel and an independent checker, to meet the spec you signed off,
except for the parts its `TRUST.md` lists as tested or trusted. Those parts are named, with the
tests behind them. The guarantee is only as good as the spec: a proof shows the code does what the
spec says, not that the spec says what you meant. That is why you review the spec before it is
frozen.

## The four statuses in `TRUST.md`
| Status | Meaning | Who checks it |
|---|---|---|
| **Proven** | A Lean theorem, checked by the kernel. The row must rest on something the audit pins: a declaration of the frozen spec, an obligation, or a pinned end-to-end theorem | `lake comparator` (sandboxed, independent kernels), the spec gates, the verified-code audit |
| **Tested against the model** | Not proven. The trusted shell (parsing, printing, the serve loop) was run against the spec's own model on random commands, and changes `mil` made to it on purpose were caught | `mil selftest` |
| **Tested** | A named test passes (for example, the CLI's exit codes, the kill test) | the app's tests |
| **Trusted** | Assumed, with the reason written down (the compiler, the operating system, `fsync`) | nobody: read these |

## What the audit checks, and what each check prevents
| Check | Prevents |
|---|---|
| `spec.lock`: every frozen file, the spec's resolved dependencies and `mil.json` are byte for byte what was signed off; the lock covers exactly the declared files | changing the spec, or the code it imports, after approval |
| Spec gates: every declaration has an `English:` doc; holes appear only in theorem statements; every spec theorem except the obligations is proven on the three standard axioms | an unreviewable spec; a spec that cannot be implemented; an unproven spec lemma |
| Spec critic: at least one planted wrong implementation or model, rejected | a spec nobody tried to break |
| Contract: the spec's holes and obligations are exactly those `mil.json` lists | a theorem that names the implementation but escapes the checker |
| `lake comparator --paranoid`, in a sandbox, on a staged copy of only the app's packages | `sorry`, custom axioms, `native_decide`, a weakened or changed statement, a redefined spec definition |
| Dependency check: the implementation requires only the spec package, defines no framework or spec module, and resolves exactly the spec's dependencies | replacing the gates, the substrate or the spec with a modified copy |
| Verified-code audit (generated by `mil` from the locked `mil.json`): no `sorry`/axioms in any verified definition or theorem; no `unsafe`, `partial`, `opaque`, `@[implemented_by]` or `@[extern]` with a body, in verified code or anything it uses; verified code does not import the shell | a binary that runs different code from the code that was proven |
| End-to-end pins (apps on the LeanKV substrate): `refines`, `pickOk` and `crash_consistent` are checked against the frozen spec's definitions | a durability theorem about a weakened stand-in |
| `mil selftest`: the shell agrees with the model; `mil`-chosen mutants of the shell are caught (score ≥ the locked minimum); every survivor explained in `TRUST.md` | a shell that ignores the verified code, or tests too weak to notice a broken shell |
| Trust rules: every cited name exists; Proven rows are anchored; "Tested against the model" cites `selftest` | a trust manifest that claims proofs nobody has |
| Shell wiring: the CLI's entry point reaches the verified functions | a shell that bypasses the verified core |

Every check has a negative test: `tests/cheats/` holds each known way to get a false AUDIT PASSED,
and CI requires every one to be rejected. Two of them were bypasses found in `mil` itself and then
fixed. A new way to cheat is added there first.

## The trust base
Always trusted, never proven: the Lean kernel and compiler and runtime; the C file layer under the
LeanKV substrate, `fsync` and the operating system; `bubblewrap`; Python (the test drivers); and `mil`
itself (it orchestrates the checks; the kernel and the comparator decide them).

## Known limits (read these before relying on an app)
- **The spec is the user's responsibility.** The framework helps you review it (English beside each
  definition, worked examples, the critic's planted bugs), but cannot know your intent.
- **The shell is tested, not proven.** In particular:
  - its I/O-failure paths (a write failing mid-command) are not reached by any test, because the
    real shell has no fault injection; they appear as explained survivors in `TRUST.md`;
  - the oracle shares the parser and printer with the shell, so a bug written into them *from the
    start* would pass the differential test (the CLI tests check literal lines; mutants do not have
    this blind spot, since the oracle is built before mutation).
- **Non-Lean shells** (for example a TypeScript HTTP layer) are checked by their own differential and
  planted-bug tests, not mutated by `mil selftest`.
- **Resources are not proven.** Proofs cover results, not time, memory or stack depth; size limits
  are tested at their bounds, speed is benchmarked.
- **Legacy apps** (no `framework_version`, created before 0.6.0) run under older rules and print a
  warning; `mil upgrade` moves them forward.
- **Evidence so far** ([RESULTS.md](RESULTS.md)): single-function tasks, two worked apps and one app
  built by another agent (Codex). No experiment has yet put an agent under pressure to cheat
  (Phase 6 W2, paused).
