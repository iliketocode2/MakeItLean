# LeanKV pilot: friction log

Phase 1 asks us to log every point of friction while following the workflow by hand. Each entry feeds Phase 2, when the framework is extracted from this pilot.

| Date | Stage | Friction | Resolution / framework implication |
|---|---|---|---|
| 2026-11-21 | 0 | The background PDFs could not be read: `poppler-utils` is missing and there is no `sudo`. | Extracted the text with `pypdf` in a scratch venv. **Framework:** the environment setup step should install `poppler-utils`. |
| 2026-11-21 | 0 | An outside reviewer (Gemini) was given only the chat summary, not the requirements doc. Most of its "please clarify" items were already in the doc. | **Framework:** reviewers, human or agent, must be given the document itself. `mil spec-review` should hand over the file, not a summary. |
| 2026-11-21 | 1 | Lean 4.36 removed `String.trimLeft`, which broke the doc-gate tool. | Used list operations instead. This confirms the toolchain-churn risk in PLAN.md. **Framework:** keep the gate tools to stable APIs and pin the toolchain. |
| 2026-11-21 | 1 | The first version of the English-doc gate flagged compiler-generated names: `.rec` and the helpers that `deriving` creates under instances. | Filter out recursors and any name nested under an instance. A negative test (one doc removed) confirmed the gate still fails when it should. **Framework:** ship `#assert_english_docs` in `lean/MakeItLean/` with that negative test. |
| 2026-11-21 | 1 | A requirement can only be enforced on an implementation the spec can see. R17 ("height ≤ c·log n") cannot be stated against an implementation whose type is left open, because its "height" could be defined as 0. | The user chose to have the spec fix a binary search tree (`Spec/Contract.lean`). Its in-order contents must equal the reference store, and its height must be ≤ 3·⌊log₂(n+1)⌋+2. A residual gap remains: shape is constrained, but how the operations use the tree is not. **Framework:** the spec-author role must ask, for each non-functional requirement, "what in the spec can see this?" |
| 2026-11-21 | 1 | The first spec used `List UInt8` everywhere, including the contract's tree. A 1 MiB value stored as a Lean list is about a million heap cells, so the implementation would have been forced to be slow. | The command, response, request, reply and recovery types are now generic over the byte type `β`. The spec uses lists; the implementation uses `ByteArray`; the contract relates them through `toBytes`. **Framework:** spec templates should be generic over the data representation from day one. |
| 2026-11-21 | 1 | While writing `recover_torn_tail`, I found that the obvious log format (magic + length + CRC) violates the approved R12. A stored value that contains a complete encoded record makes a torn write look like corruption, so the store would refuse to open. | Byte-stuffing in `Spec/Log.lean`: the magic can then appear only at the start of a record (`magic_only_at_start`). A computational check confirmed that every truncation of such a record is a torn tail. **Framework:** this is the DeepMind lesson that writing the theorem statement is what exposes the spec gap. The spec-critic role should look for the user's data imitating the format's own structure. |
| 2026-11-21 | 1 | The store-layer theorems were checked for teeth before Stage 2, using a throwaway reference store and three planted bugs. All were evaluated over 728 fault/crash scenarios. The reference passed everything, and each bug failed between 42 and 126 scenarios. | This is cheap (about 10 s, interpreted) and catches vacuous or over-strong statements before freeze. **Framework:** `mil validate` should run a spec-critic step like this: an honest model plus planted bugs, checked against each theorem's statement by evaluation. The prototype is the seed of the R23 oracle. |
| 2026-11-21 | 1 | `List.Forall₂` is in Mathlib, not core. The structure constructors `.mk` were flagged by the doc gate. | Wrote a small `repliesMatch` instead, and exempted auto-generated structure constructors in the gate. |
| 2026-11-21 | 2 | Proving the spec-level theorems took several iterations each. Recurring traps in Lean 4.36: unfolding a constant inside `decide` breaks its instance (convert to a Prop first); `simp` cannot use equation lemmas for definitions with overlapping wildcard patterns (use `delta`); `List.Forall₂`, `Nat.strong_induction_on`, `le_trans` and `List.drop_append_of_le_length'` are Mathlib names or renamed; several `if_pos`/`dif_pos` variants are deprecated. | All 124 spec-level theorems are proven, using only the standard axioms (checked over every spec theorem with `collectAxioms`). **Framework:** ship a "Lean 4.36 proof idioms" note in `knowledge/` so agents don't rediscover these. |
| 2026-11-21 | 2 | The contract critic's random tests first used 6 keys, so the unbalanced "chain" bug passed: a height of 6 is still within 3·⌊log₂ 7⌋+2. | Widened to 26 keys and 60 commands; the chain is now caught in 298/300 runs. **Framework:** each critic needs a check that its generator reaches the regime where each property bites (here, n ≥ 12). |
| 2026-11-21 | 2 | The first `SPEC_REVIEW.md` generator mis-parsed theorem statements that contain `let x := …` or `(m := FsM)`, and reported 4 unproven store theorems as "Proven". | The parser now tracks bracket depth and skips `let` bindings. It was cross-checked against Lean's own `collectAxioms`: exactly 9 theorems use `sorry`, matching the review. **Framework:** generate the review from the elaborated environment (proof status from `collectAxioms`), not from the source text. |
